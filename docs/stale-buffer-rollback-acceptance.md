# Stale-buffer rollback acceptance matrix

Invariant: saving or reconnecting must never remove a collaborator edit or a previously confirmed user edit. When the extension cannot prove the restored buffer's ancestry, it must send no update and keep the local buffer recoverable.

| ID | Scenario | Required observable result |
| --- | --- | --- |
| P0 | Hot exit restores a dirty stale buffer; the server contains later confirmed-user and collaborator edits; no trusted base is available | No `applyOtUpdate`; server text and version are unchanged; save fails closed; the exact local text remains dirty |
| P1 | Startup `readFile` joins the latest server snapshot before the host overlays its stale backup | The fresh read is not accepted as the backup's ancestry; result is the same as P0 |
| P1a | A single editor object is first observed clean with the latest remote text and then receives a stale hot-exit overlay | The clean observation remains quarantined; the stale overlay sends no update and remains dirty |
| P2 | Restored text exactly equals the authoritative snapshot, but provenance is unavailable | Safe no-op; no wire update; save may complete |
| M1 | A trusted base belongs to another window or to another project with the same pathname and document ID | The wrong-scope base is ignored; no update is sent; authoritative and local text remain unchanged |
| B1 | A normal clean open starts from a provider read | The editor stays quarantined until `Reload Remote and Enable Editing` confirms the unchanged document object, URI, buffer, version, text, sender, generation, and fresh authoritative snapshot; cancellation or any intervening change leaves it untrusted and sends no update |
| B2 | A normal edit starts from the explicitly confirmed exact joined base | One effectful update at the joined version; applying its operations to the base yields the requested text |
| C1 | Same-generation local `contentChanges` and consecutive remote `update.op` entries prove disjoint edits from one exact base | The actual local operation is transformed through each actual remote operation in version order; the server retains both edits; if the merged server text differs from the host save witness, the provider save is rejected and the host stays dirty until an exact remote reload is confirmed |
| C2 | Actual local and remote operations overlap, share a deletion boundary, or insert at the same position | No update; remote text is unchanged; local text remains recoverable as a conflict |
| C3 | Local change events are missing, contain multiple unordered changes, skip an editor version, or do not replay exactly; or a remote event has a missing/non-integer revision, a ledger gap, or a malformed operation | No update; snapshots are not used to infer the missing causal history; local text remains dirty and recoverable |
| C4 | One socket generation and causal epoch report two different operations for the same document revision | The document session and causal epoch are invalidated; a fresh join may recover authoritative text, but the ambiguous local save emits no update |
| R1 | A warm document session disconnects, the server advances, and the session rejoins | The old causal epoch is invalidated; the retained durable base remains recovery evidence only; no effectful update is sent until an exact remote reload establishes a new base |
| R2 | The queue acknowledgement is lost before the update is applied | One retry carries the original version and operations; one logical application and one collaborator broadcast result |
| R2a | The queue acknowledgement succeeds while application and sender confirmation are held | The save remains pending and authoritative text remains unchanged until the separately released application is confirmed |
| R2b | The payload Redis enqueue succeeds, the notification enqueue fails, and the server disconnects before its callback can be delivered | The write remains durably pending with its original public ID; a fresh-identity retry carries that ID in `dupIfSource`; consecutive unknown outcomes extend the stable source chain; exactly one logical application results |
| R2c | A collaborator operation causes a document-room `otUpdateError` while this client's valid operation is queued | The document-wide error is not attributed to the local operation because it has no sender or operation identity; local pending and dedupe evidence remain intact until fresh join and sender confirmation reconcile the outcome |
| R3 | The update is applied but its queue acknowledgement and sender confirmation are lost | A retry carries prior public IDs in `dupIfSource`; it has no second effect and no second collaborator broadcast |
| I1 | Two windows access the same project and document while one has an outcome-unknown pending update | Bases, pending updates, acknowledgements, and public-ID chains remain window-local; an intervening edit from the other window survives recovery |
| I2 | Two projects share the same pathname and document ID | Provenance and pending updates remain project-scoped; neither project can authorize or consume the other's save |
| I3 | Encoded, decoded, or reordered project-query aliases expose two dirty buffers for one logical document | The aliases share one project connection; ambiguous effectful saves emit no update and preserve both local buffers |
| J1 | A project join returns a project `_id` different from the requested project | The session terminates before state is exposed, documents are joined, or an initial compile is requested |
| J2 | A document join returns nonempty `updates`, contradicting the pinned no-`fromVersion` request contract; or its snapshot/join-time live catch-up contains a revision that is not a nonnegative safe integer, a malformed outer shape or operation, a pre-snapshot revision, revision gap, unproven op-less confirmation, conflicting duplicate, or operation that cannot replay exactly against the snapshot | Contradictory response updates or an invalid snapshot/live catch-up batch reject the entire join atomically; no valid causal epoch is exposed; a dirty public save emits no OT and remains recoverable |
| S1 | The same stale buffer is reached through manual save, autosave, or compile `saveAll` | Every route uses the same fail-closed gate; a blocked initial `saveAll` prevents compilation |
| X1 | A blocked recovery dialog remains open while the document is closed and reopened at the same URI | Neither recovery-copy nor reload acts on the replacement buffer; a valid copy uses the original buffer's bytes at dialog completion |
| X2 | `Reload Remote` is selected while the cached document snapshot is stale or the remote advances during recovery | Recovery performs a fresh document join and binds the exact buffer, sender generation, revision, and text. Movement before the replacement save linearizes leaves it unsaved. If the remote advances strictly after a successful save at $A@v$, the host may remain temporarily clean at $A$; $A@v$ remains the causal base, and the next local edit transforms against the later remote revision without removing its bytes |
| U1 | A user save is confirmed under an earlier public ID, then collaborator work advances the server before restart | A restored stale buffer cannot remove either confirmed region; the save fails closed and remains recoverable |
| N1 | A dirty editor saves a genuinely missing text path | The save fails before `/entities`, `addDoc`, `uploadFile`, `joinDoc`, or OT; no empty remote document is created; the exact local text remains dirty and recoverable |
| N1a | A collaborator creates a different document at that path after `onWillSave`, including one whose text equals the local bytes | The unbound editor incarnation cannot acquire the collaborator document's identity from the changed path cache; repeated saves fail before `joinDoc` or OT and remain dirty |
| N1b | Internal or future code calls the direct VFS text-creation helper with empty or nonempty content | The helper reports `Unavailable` before project entities, `addDoc`, `uploadFile`, `joinDoc`, or OT; the remote project is unchanged |
| N2 | A future server contract proposes to enable new text creation | It must atomically create-if-absent with initial content, or condition the initial write on document ID, expected path, and a structure revision within one transaction; path-only pre/post snapshots do not qualify |

The deterministic server oracle separates three events: queue acknowledgement, effectful application, and sender-only version confirmation. A deduplicated `dupIfSource` retry is permitted on the wire; duplicate text application or duplicate collaborator broadcast is not.

Outcome-unknown handling follows the same pinned server source. The document updater [enqueues the update payload and its notification in separate Redis operations](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/real-time/app/js/DocumentUpdaterManager.js#L127-L143), while the realtime controller [disconnects the client before returning a queue error through the callback](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/real-time/app/js/WebsocketController.js#L606-L648). A payload may therefore have been accepted even when the client receives no acknowledgement. Separately, the document updater's error payload [contains only project ID, document ID, and error](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/document-updater/app/js/UpdateManager.js#L263-L270), and the realtime service [broadcasts it to every client in the document room before disconnecting them](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/real-time/app/js/DocumentUpdaterController.js#L175-L183). Such an error cannot prove which client's operation failed, so it must retain pending and deduplication evidence.

New-text creation remains disabled under the public contract pinned to Overleaf commit `28ad3b03b71cb4311decdcb55c36b33ec10d72db`. [`addDoc` returns the created document identity](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/web/app/src/Features/Editor/EditorHttpController.mjs#L133-L163), but the [`/entities` response exposes only path and type](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/web/app/src/Features/Project/ProjectController.mjs#L376-L390). Neither a project-tree snapshot nor `joinDoc` prevents the created document from being renamed away and another document from taking its original path before the initial OT is sent. Therefore a path check cannot atomically bind path, document ID, and initial text. A dirty editor incarnation which was never bound by a clean provider read remains unbound even if a document later appears at the same path; a path-cache update cannot promote it into a save witness. [`uploadFile` also enables replacement](https://github.com/overleaf/overleaf/blob/28ad3b03b71cb4311decdcb55c36b33ec10d72db/services/web/app/src/Features/Uploads/ProjectUploadController.mjs#L84-L149) and is never a safe fallback.

The following assumptions still require host or deployment verification:

- Rejected `FileSystemProvider.writeFile` calls keep restored buffers dirty and recoverable in each supported VS Code and Cursor version.
- `Reload Remote` in each supported host replaces only the exact blocked editor and treats the successful save as the causal linearization point: movement before it does not become clean; movement after it may leave $A$ temporarily clean, but the next local edit preserves the later remote bytes.
- Ordinary clean opens in each supported VS Code and Cursor version present the confirmation once, remain quarantined on cancellation, and invalidate confirmation if a hot-exit overlay arrives first.
- A rejected genuinely new text save preserves the exact dirty buffer without invoking any remote creation or upload endpoint in each supported host.
- Hosted Overleaf and supported self-hosted releases implement the current open-source `dupIfSource`, sender-confirmation, retention-window, and `joinDoc` ordering semantics.
- Recovery records are not automatically expired; obsolete records may require later storage housekeeping, but they never confer cross-window write authority.
- Alternative/HTTP-backed mode deliberately blocks revision-unproven whole-document saves rather than staging them as realtime OT.

The version-2 provenance schema binds canonical server, verified user, project, document, logical editor identity, extension-host session, exact buffer incarnation, base revision/content, and dirty content. Integrity or schema mismatches fail closed. Cold records are recovery evidence only: they never authorize a restarted window, and multiple exact candidates are reported as ambiguous.
